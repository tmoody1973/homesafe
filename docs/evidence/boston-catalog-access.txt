MOO-608 — SAM ingest. 2026-08-13.
================================================================

--- The two records verified before any code existed ---
Both came from querying Boston's own SAM service directly and were written
into docs/address_302_sumner_to_parcel.json before the schema was designed.
They now come back from our database identically:

  SAM 132380 -> 302 Sumner St      parcel 0104910000  building 130883
  SAM 130392 -> 181-183 State St   parcel 0303807000  building 136572

The second confirms a hyphenated street-number range survives ingest intact.

--- Row count is 399,452, and that is correct ---
Expected roughly 190k and got twice that, so it needed explaining rather
than accepting:

  total rows                399,452
  distinct sam_address_id   399,452   <- no duplicates; the unique key holds
  rows with a unit value    267,501   <- SAM is UNIT-level
  distinct parcels          126,789

SAM assigns an id to individual apartments, not just street addresses:
  20 Washington St 407  unit 407  sam 329287
  360 Meridian St 9     unit 9    sam  94519

So 399k is street addresses plus units. No rows have a blank full_address
and none has a null sam_address_id.

--- FINDING: violations are building-level, not apartment-level ---
Took the distinct sam_id values from the live violations file and looked at
what they actually point at in SAM:

  violation sam_ids sampled     4,000
  resolved to a SAM address     3,903  (97.6%)
  ...of which ADDRESS-level     3,882  (99.5%)
  ...of which UNIT-level           21  (0.5%)
  unresolvable                     97  (2.4%)

Two consequences, both for the interface rather than the pipeline:

1. `address_scope = 'address'` for violations is now empirically justified
   rather than assumed. A resident asking "is there a record about MY
   apartment?" must be told "there is a record about your building" — those
   are different statements, and 99.5% of the time only the second is true.
   The scope badge is the whole difference.

2. About 2.4% of violations carry a sam_id absent from the current SAM file
   — retired or superseded ids. Those cannot be attached to a canonical
   address and must be shown as unmatched rather than dropped silently.

MOO-609 — address resolution. 2026-08-13.
================================================================

--- Before indexing: a full scan of 399,452 rows per lookup ---
  resolveAddress("302 Sumner St")   1,900ms

  EXPLAIN:
    • filter
    │ filter: upper(full_address) = '302 SUMNER ST'
    └── • scan
          estimated row count: 31 - 399,452 (100% of the table)
          spans: FULL SCAN (SOFT LIMIT)

Cause: the query wraps the column in upper(), and an index on a column
cannot serve a query that transforms that column. The three existing
indexes (parcel_id, sam_address_id, and zip-leading street index) were all
unusable for this.

--- After migration 004 ---
  EXPLAIN:
    └── • scan
          estimated row count: 10 (<0.01% of the table)
          table: address_entity@address_entity_upper_full_address_idx
          spans: [/'302 SUMNER ST' - /'302 SUMNER ST']

  timings (pool warmed, so this is query time not TLS setup):
     53ms   1 candidate   302 Sumner St        132380  high
     47ms   1 candidate   181-183 State St     130392  high
     89ms  10 candidates  1 City Hall Sq       414498  ambiguous
     74ms   0 candidates  99999 Nowhere Blvd   (none)

1,900ms -> 53ms. Same query, same data, same application code.

--- The ambiguity case fired on real data, unprompted ---
`1 City Hall Sq` returns TEN candidates and reports `ambiguous`, not `high`.
This is the behaviour FR-01 exists for: the resolver presents a list and the
resident chooses. It matters because SAM is unit-level — a street address in
a multi-unit building legitimately matches the building and every apartment
in it, so ambiguity is the common case rather than an edge case. The plan was
written expecting this branch to be hard to trigger.

--- Partial migration is a reachable state in CockroachDB ---
Migration 004 first failed with `Connection terminated unexpectedly`. After
the failure the FIRST index existed, the second did not, and the migration
was not recorded as applied — despite the runner wrapping each file in a
transaction.

Index creation in CockroachDB is an async background job that had already
committed, so the transaction did not roll it back. Recovery worked only
because both statements were written CREATE INDEX IF NOT EXISTS.

Rule going forward: CockroachDB schema-change statements must be
individually idempotent. The surrounding transaction will not save you.
